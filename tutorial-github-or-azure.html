1  How to use this guide

This is a "one-shot" curriculum: follow it top to bottom over a weekend and you will have installed a professional toolchain, built two working projects, and — crucially — learned to direct an AI coding agent rather than just chat with it.

The mindset shift

Claude Code isn't autocomplete and it isn't a chatbot in a side panel. It's an agent that lives in your terminal, reads and writes files in your project, runs commands, and iterates. Your job moves up a level: you describe intent, review diffs, steer architecture, and verify results. The developers who interview well in 2026 aren't the ones who can type the most code — they're the ones who can decompose a problem, give an agent crisp context, and catch when its output is wrong. That skill is what this weekend trains.

Read every diff. The single habit that separates people who get value from Claude Code from people who get burned: never accept a change you haven't looked at. This guide will remind you, but make it reflex.

How the prompts are formatted

Throughout the guide, text you type into Claude Code appears in green blocks like this:

▶ Prompt to Claude Code
Explain what this repository does in three sentences, then list the files you'd need to change to add a health-check endpoint.

Commands you run yourself in PowerShell or a terminal appear in dark blocks:

claude --version

2  Part 1 — Let Claude Code set up your machine

Here's the twist that makes this fun: you'll do only two things by hand — create your Git host account and install Claude Code itself (it obviously can't install itself). After that, Claude Code installs and configures the entire rest of the toolchain for you by running commands, which you approve as they go.

How this works Claude Code can run shell commands in your terminal. On Windows it uses winget (the built-in package manager) to install software, and a Git-host CLI (the GitHub CLI or the Azure CLI) to create repos and pull requests — no manual downloads or installer wizards. It asks permission before each command; you watch and approve.
Choose your Git host This edition supports two hosts — pick one and follow its blocks throughout (they're colour-coded GitHub and Azure DevOps). GitHub is the default for open-source and public portfolios — easiest to share with an interviewer. Azure DevOps is what many enterprises (especially .NET shops) use day to day, so it's excellent interview signal if you're targeting those companies. The app you build is identical either way; only the repo, auth, and pull-request commands differ. You can even do the warm-up on one host and the capstone on the other to learn both.

2.1  Create your Git host account (the only account you make by hand)

Your Git host is where your code lives and where an interviewer will look at your work. Account signup can't be automated, so do this one manually. Follow the block for the host you chose. If you already have an account/org, skip to 2.2.

▶ GitHub
  1. Go to github.com/signup and create an account using your email. Pick a professional username — it becomes part of your portfolio URL (github.com/<you>).
  2. Verify your email address.
  3. Enable two-factor authentication (Settings → Password and authentication). GitHub requires 2FA for contributors, and interviewers notice a locked-down account.
▶ Azure DevOps
  1. Go to dev.azure.com and sign in with a Microsoft account (create a free one if needed). Azure DevOps is free for small teams.
  2. When prompted, create an organization — this is your top-level container, at dev.azure.com/<org>. Pick a sensible name.
  3. Inside the org, create a project (e.g. bootcamp). A project holds your Git repos, boards, and pipelines. Set visibility to Private (the default). You'll create the individual repos later with the CLI.

Note the two names you chose — your organization and project — you'll hand them to Claude in step 2.5.

2.2  Install the Claude Code CLI (the one manual install — bootstrap)

This is the only piece of software you install yourself, because it's the tool that will install everything else. On Windows the recommended path is the native installer — a single PowerShell command, no Node.js or admin rights required. It downloads the binary, updates your PATH, and wires up shell hooks.

Run in PowerShell (not Command Prompt)
irm https://claude.ai/install.ps1 | iex
Two gotchas everyone hits (1) This must run in PowerShell. If you see 'irm' is not recognized, you're in the old Command Prompt — open "Windows PowerShell" instead. (2) When it finishes, close the terminal and open a brand-new one. The PATH change only applies to new shells; your current window still can't find claude.

In a fresh PowerShell window, verify:

claude --version

2.3  First launch and login

Create a scratch folder, move into it, and start Claude Code:

mkdir C:\dev
cd C:\dev
claude

On first run it opens a browser to authenticate. Sign in with your Claude account (a Claude Pro or Max subscription, or Claude API credits, powers the CLI). Once authenticated, you'll drop into the interactive Claude Code prompt inside your terminal. Type /help to see the slash commands.

2.4  Have Claude Code install the rest of your toolchain

Now let the agent take over. From the running Claude Code session in C:\dev, give it this prompt. It will install Git, Visual Studio Code, and Node.js via winget, set up your Git identity, and add the VS Code extensions you'll need — verifying each step.

▶ Prompt to Claude Code
Set up this Windows machine for full-stack development. Do it step by
step, showing me each command before you run it:
1. Use winget to install Git ( Git.Git ), Visual Studio Code
   ( Microsoft.VisualStudioCode ), and the Node.js LTS ( OpenJS.NodeJS.LTS ).
2. Configure my Git identity — ask me for my name and the email on my
   Git host account, then set user.name, user.email, and
   init.defaultBranch = main globally.
3. Install these VS Code extensions with `code --install-extension`:
   C# Dev Kit (ms-dotnettools.csdevkit), Angular Language Service
   (Angular.ng-template), and SQL Server (ms-mssql.mssql).
4. Verify everything: print `git --version`, `node --version`,
   `npm --version`, and `code --version`.
If a winget install needs elevation, tell me and I'll approve the UAC prompt.
Two things to expect (1) Some installs pop a Windows UAC/admin prompt — approve it. (2) Newly installed tools land on your PATH, but the current session may not see them. If a verify step fails with "not recognized," exit Claude Code, open a fresh PowerShell, and run claude again from C:\dev — then ask it to re-run the verification.

2.5  Connect Claude Code to your Git host

So Claude can create repos and open pull requests for you, have it install and authenticate the CLI for your chosen host. You'll complete one browser step; Claude drives the rest.

▶ GitHub
▶ Prompt to Claude Code
Install the GitHub CLI with winget ( GitHub.cli ), then run `gh auth login`
to authenticate me to GitHub over HTTPS. Walk me through the browser/device
step. When it's done, confirm with `gh auth status` and `gh api user`
to show my logged-in username.

Follow the on-screen device-code prompt in your browser. Once gh auth status reports you're logged in, Claude can create repositories on your behalf.

▶ Azure DevOps

Azure DevOps uses the Azure CLI (az) plus its azure-devops extension for repo/PR commands, and Git Credential Manager (bundled with the Git you installed in 2.4) for push authentication. Give Claude your org and project names from step 2.1.

▶ Prompt to Claude Code
Set me up to use Azure DevOps from the CLI, showing each command first:
1. Install the Azure CLI with winget ( Microsoft.AzureCLI ).
2. Run `az login` and walk me through the browser sign-in.
3. Add the DevOps extension: `az extension add --name azure-devops`.
4. Set my defaults so I don't repeat them:
   `az devops configure --defaults organization=https://dev.azure.com/
   project=` — ask me for  and  first.
5. Verify with `az repos list --output table` (an empty list is fine — it
   proves auth and defaults work).
Git Credential Manager will handle the browser prompt the first time we
push to Azure DevOps, so no PAT is needed.

Once az repos list runs without an auth error, Claude can create repositories in your project.

A note on repo visibility On GitHub you choose public or private per repo (Part 2 covers this). On Azure DevOps, repos live inside your private project and are visible to project members — there's no one-command "make it public." That's exactly how most corporate code is kept, which is fine; if you want a public portfolio piece, use GitHub for that one, or later mirror the repo to GitHub.

2.6  The core Claude Code workflow (learn this now)

Everything else in this guide is a variation on a handful of moves. Skim them now; they'll click once you're building.

MoveWhat it is / how
Interactive sessionRun claude in a project folder. Claude can read/write files there and run commands, asking permission before actions that change things.
One-shotRun claude -p "your prompt" to get a single answer without entering the interactive UI — handy in scripts.
Plan modePress Shift+Tab to cycle modes. "Plan mode" makes Claude propose an approach and wait for your approval before editing anything. Use it for anything non-trivial.
CLAUDE.mdA file at your repo root that Claude reads automatically every session — your project's standing instructions (stack, conventions, commands). On an existing codebase, run /init to generate a first draft; on a new/empty repo, just ask Claude to create one from your description.
Slash commands/init, /clear (reset context between tasks), /review, /mcp (manage MCP servers), /help.
Reviewing changesClaude shows a diff before applying edits. Read it, then approve or reject. Approve narrowly at first; broaden as you trust it.
Context hygieneRun /clear when you switch to an unrelated task so old context doesn't confuse the model.
The golden loop Describe → let Claude plan → approve → review the diff → run/test → commit. Repeat in small slices. Small slices are the whole trick — a tight task with a clear "done" beats a giant vague one every time.

2.7  Commit early, commit often

By default Claude tends to batch its work and commit at the end. Frequent, small commits are a better habit — each one is a clean checkpoint you can review or roll back to, and it's exactly how you'll work on a real team. The most reliable way to enforce this is to make it a standing rule in your CLAUDE.md so Claude follows it every session without being reminded.

Once you've created a project's CLAUDE.md (next section), add the rule to it:

▶ Prompt to Claude Code
Add a "Git workflow" rule to CLAUDE.md: after completing each logical
change — a feature, a fix, or a refactor that leaves the app working —
stage and commit it immediately with a clear conventional-commit message,
rather than batching everything into one commit at the end. Always show me
the diff and the proposed message before committing, and never commit
secrets or build artifacts.

You can also invoke it ad-hoc at any time in a session:

▶ Prompt to Claude Code
From now on in this session, commit after each logical change instead of
waiting until the end. Show me the message before each commit.
Tip "After each logical change" beats "after every edit" — you want one commit per meaningful unit of work (a working feature), not a commit for every one-line tweak. If Claude commits too coarsely or too finely, just say so; it will adjust.

2.8  Work on feature branches, not directly on main

On real teams, nobody commits straight to main. Instead you create a short-lived feature branch for each piece of work, commit there, push it, open a pull request (PR), and merge it back into main after review. It keeps main always-working, makes changes reviewable in isolation, and — for your portfolio — shows an interviewer you know the professional Git flow. Even solo, it's worth doing.

The cycle for each feature is the same idea on both hosts; only the PR commands differ:

▶ GitHub
git switch -c feat/scoreboard # 1. branch off main … build + commit on the branch (small commits) … git push -u origin feat/scoreboard # 2. push the branch gh pr create --fill # 3. open a pull request gh pr merge --squash --delete-branch # 4. merge it, tidy up git switch main && git pull # 5. update local main
▶ Azure DevOps
git switch -c feat/scoreboard # 1. branch off main … build + commit on the branch (small commits) … git push -u origin feat/scoreboard # 2. push the branch az repos pr create --source-branch feat/scoreboard \ --target-branch main --title "Scoreboard" --open # 3. open a PR az repos pr update --id --status completed \ --delete-source-branch true # 4. complete it, tidy up git switch main && git pull # 5. update local main

Make it a standing rule so Claude does it for you — you'll fold this into your first project's CLAUDE.md in Part 2 (Claude already knows which host you configured, so it'll use the right commands). The rule to add:

▶ Prompt to Claude Code
Add a "Branching" rule to CLAUDE.md: never commit directly to main. For
each new feature or fix, create a feature branch named feat/
or fix/, make the small commits there, push the branch, and
open a pull request using my Git host's CLI — `gh pr create --fill` for
GitHub, or `az repos pr create --source-branch  --target-branch
main --title "..."` for Azure DevOps. After I approve, complete/merge the
PR (`gh pr merge --squash --delete-branch`, or `az repos pr update --id
 --status completed --delete-source-branch true`) and switch back to
main. Confirm the branch name with me before you start each one.

Or turn it on ad-hoc for the next piece of work:

▶ Prompt to Claude Code
Before we build this, create a feature branch feat/ and do all the
work there. When it's done and committed, push it and open a PR — don't
merge until I say so.
The full professional loop Combine the last three sections: branch → small commits as you go → push → PR → review → merge → pull main. That's the everyday rhythm at most companies, and being able to narrate it — and show branches and merged PRs in your repo — is a real interview signal.

3  Part 2 — Warm-up build: Tic-Tac-Toe

You'll build a playable browser game with zero framework overhead. The point isn't the game — it's rehearsing the agent loop end to end: repo, CLAUDE.md, branch, plan mode, iterate, test, commit, push, PR, merge.

Because you connected your host's CLI in Part 1, Claude can create the repo and clone it locally in one shot. Start a session in your dev folder:

cd C:\dev

▶ GitHub
▶ Prompt to Claude Code
Using the GitHub CLI, create a new PRIVATE GitHub repo called
"tic-tac-toe" with a README, then clone it into C:\dev\tic-tac-toe.
Use: `gh repo create tic-tac-toe --private --add-readme --clone`.

▶ Azure DevOps
▶ Prompt to Claude Code
Using the Azure DevOps CLI, create a new Git repo named "tic-tac-toe" in

You can also let Claude open the folder in VS Code:

▶ Prompt to Claude Code
Open C:\dev\tic-tac-toe in VS Code with `code C:\dev\tic-tac-toe`.

cd C:\dev\tic-tac-toe

From here on, Claude is working inside the repo, so its file edits and Git commands land in the right place. (If you'd rather not restart, Claude can instead work from C:\dev and write to full C:\dev\tic-tac-toe\... paths — it works, just with longer paths. Restarting is cleaner.)

3.2  Create your CLAUDE.md

From inside the tic-tac-toe folder, in your Claude Code session, set up project memory.

Don't use /init on an empty repo The /init command works by scanning an existing codebase and summarizing it. Your repo is brand-new (just a README), so /init has nothing to document — Claude will correctly tell you it won't invent content. That's expected. Instead, describe the project you're about to build and have Claude write the CLAUDE.md from that. (You'll use /init later, on real code.)
▶ Prompt to Claude Code
Create a CLAUDE.md for this project. It is a browser-based Tic-Tac-Toe
game built with plain HTML, CSS, and vanilla JavaScript — no frameworks,
no build step. Conventions: one index.html, one styles.css, one game.js.
Keep game logic pure and separated from DOM code so it can be unit tested.
The app is opened by double-clicking index.html.
Git workflow: never commit directly to main. Create a feature branch
(feat/) per feature, commit after each logical change with a clear
conventional-commit message — don't batch everything into one commit at
the end — then push the branch and open a PR using my Git host's CLI
(GitHub `gh pr create --fill`, or Azure DevOps `az repos pr create`).
Show me the diff and message before each commit.

Review the diff, approve it, and you've just created your project's standing context.

3.3  Start your feature branch

Before writing any game code, follow the rule from Part 1: branch off main first, so every commit lands on the branch and main stays clean. From your Claude Code session:

▶ Prompt to Claude Code
Before we build anything, create and switch to a feature branch called
feat/game (git switch -c feat/game). Confirm we're on it, then do all the
game work and commits here — never on main.

Everything you build next happens on feat/game. You'll push it and open the pull request once the game works and is tested.

3.4  Build the game with plan mode

Press Shift+Tab until the mode indicator reads plan. Then:

▶ Prompt to Claude Code
Build the complete Tic-Tac-Toe game described in CLAUDE.md.
Requirements:
- 3x3 grid, two human players alternating X and O
- Detect wins (rows, columns, diagonals) and draws
- A status line showing whose turn it is / who won
- A "New game" button that resets the board
- Clean, modern styling with hover states and a subtle win highlight
Keep the win-detection logic in a pure function I can test later.
Show me your plan first.

Claude will propose a plan and file list. Read it. If it looks right, approve. It then creates index.html, styles.css, and game.js, showing you each diff. Approve them.

3.5  Run it and iterate

Open index.html by double-clicking it in the file explorer (or in VS Code, right-click → "Reveal in File Explorer"). Play a few rounds. Found something to change? Just say so:

▶ Prompt to Claude Code
Two things: the winning three cells should flash green for a moment,
and add a running scoreboard (X wins / O wins / draws) that persists
across "New game" but resets on page reload.

This is the loop that matters: observe → describe the change in plain English → review the diff → refresh the browser. Do it a few times until the game feels polished.

3.6  Add tests

Even for a toy app, practice the habit interviewers care about — testing the pure logic.

▶ Prompt to Claude Code
Extract the win-detection and board logic into a testable module and
add a small Node-based test suite using the built-in node:test runner
(no external dependencies). Cover: row win, column win, both diagonals,
a draw, and an in-progress board. Add an npm "test" script. Then run the
tests and show me the output.

Claude will refactor, write tests, wire up package.json, and run npm test for you. If a test fails, ask it to fix the code (not the test) and re-run. This "red → green" cycle is exactly what you'll do on real teams.

3.7  Open a pull request and merge

Your work is already on feat/game, so there's nothing to untangle — just push it and open the PR. Claude knows which host you set up, so it'll pick the right commands:

▶ Prompt to Claude Code
Push the feat/game branch and open a pull request describing the game and
its tests, using my Git host's CLI (GitHub: `gh pr create --fill`; Azure
DevOps: `az repos pr create --source-branch feat/game --target-branch main
--title "Tic-Tac-Toe game and tests" --open`). Show me the commit messages
and PR title before you push, then give me the PR URL.

Open the PR URL — this is where a reviewer would comment on a team. Since it's your repo, you can complete it yourself:

▶ Prompt to Claude Code
Complete/merge the PR, then switch back to main and pull so my local main
is up to date. Use GitHub `gh pr merge --squash --delete-branch`, or Azure
DevOps `az repos pr update --id  --status completed
--delete-source-branch true`.

Refresh your repo in the browser — you'll see the merged/completed PR and your game on main. You've now done the complete professional cycle: branch → plan → build → iterate → test → small commits → push → PR → merge, all directed through the CLI — on the host of your choice.

Optional stretch Ask Claude to add an unbeatable computer opponent using the minimax algorithm, then have it explain minimax to you line by line. Great interview fodder and a good test of using Claude to learn, not just to produce.

4  Part 3 — The capstone: full-stack task tracker

Now the real thing: a three-tier application on the exact stack you'll be interviewed on. You'll build a Task Tracker — an Angular UI, a C# Web API, and a SQL Server database — then connect a database MCP so Claude can inspect the data directly.

4.1  The architecture

Three tiers, each with one job. Understanding this diagram — and being able to draw it on a whiteboard — is half of a full-stack interview.

┌──────────────────────────────────────────────┐ │ FRONT END · presentation tier │ │ Angular 22 SPA — TypeScript, signals │ │ http://localhost:4200 │ └──────────────────────────────────────────────┘ │ HTTP request (JSON) ▲ JSON response ▼ │ ┌──────────────────────────────────────────────┐ │ MIDDLE TIER · application tier │ │ C# / .NET 10 Web API — Controllers + EF Core │ │ REST endpoints at http://localhost:5xxx │ └──────────────────────────────────────────────┘ │ LINQ → SQL (EF Core) ▲ result sets ▼ │ ┌──────────────────────────────────────────────┐ │ BACKEND · data tier │ │ SQL Server 2025 Express — TaskTrackerDb │ │ Tasks table │ └──────────────────────────────────────────────┘
  • Backend (data tier): SQL Server 2025 Express stores the data in a Tasks table.
  • Middle tier (application tier): A C#/.NET 10 Web API exposes REST endpoints (GET/POST/PUT/DELETE /api/tasks) and uses Entity Framework Core to talk to the database.
  • Front end (presentation tier): An Angular 22 single-page app calls the API over HTTP and renders the UI.

4.2  Have Claude Code install the capstone toolchain

Three more tools to install — and again, Claude does the work. Start a Claude Code session in C:\dev and give it this prompt.

▶ Prompt to Claude Code
Install the toolchain for a .NET + Angular + SQL Server capstone, showing
each command first and verifying as you go:

   `dotnet --version` (expect 10.x).
2. SQL Server 2025 Express. Try winget first

For the MCP later, you'll enable mixed-mode auth, create a login, and turn on TCP/IP; Part 4 covers that (and Claude can do it). For now, Windows auth is fine.
If a winget package isn't found Package IDs and availability shift over time. If Claude reports it can't find, say, the SQL Server 2025 Express ID, let it fall back to the official installer — or run winget search "SQL Server" and tell Claude which ID showed up. Remember to restart Claude Code in a fresh terminal after installs so new CLIs (dotnet, ng) are on its PATH.

5  Part 4 — Add a SQL Server MCP to Claude Code

The Model Context Protocol lets Claude Code connect to external systems through standard "servers." You'll add a SQL Server MCP so Claude can inspect your schema and run queries against TaskTrackerDb directly — turning it into a database-aware pair programmer.

5.1  What an MCP actually is

An MCP server is a small program that exposes tools (and sometimes data resources) over a standard protocol. Claude Code launches the server, discovers its tools, and can call them on your behalf — with your approval. A SQL Server MCP typically exposes tools like "list tables," "describe a table," and "run a read-only query." The value: instead of you copy-pasting schema into a prompt, Claude can go look for itself. This is the same mechanism companies use to give AI agents safe, governed access to internal systems — which is why it comes up in interviews.

Prefer read-only For learning, register the MCP in a read-only mode (query and inspect, no writes). It keeps Claude from ever altering your data by accident, and it mirrors how responsible teams scope agent access in production.

5.2  Prepare a database login for the MCP

Most SQL Server MCP servers connect with a username/password (SQL authentication) rather than Windows auth. Set that up once in SSMS:

  1. In SSMS, right-click the server → Properties → Security → select "SQL Server and Windows Authentication mode". Click OK.
  2. Right-click the server → Restart (mixed mode needs a restart).
  3. Under Security → Logins, create a new login — e.g. mcp_reader with a password — and grant it read access to TaskTrackerDb (map the login to the database with the db_datareader role).
Let Claude help You can ask Claude Code to generate the exact T-SQL for creating a read-only login and role membership, then run it in SSMS. Prompt: "Give me T-SQL to create a SQL login 'mcp_reader' with a password, mapped to TaskTrackerDb with only db_datareader."

5.3  Enable TCP/IP so the MCP can connect

SQL Server Express installs with the TCP/IP protocol disabled — out of the box it only listens on shared memory / named pipes. The MCP server connects over TCP, so turn it on once:

  1. Open SQL Server Configuration Manager.
  2. Under SQL Server Network Configuration → Protocols for SQLEXPRESS, right-click TCP/IP → Enable.
  3. Double-click TCP/IP → IP Addresses tab → scroll to IPAll and set TCP Port to 1433 (clear TCP Dynamic Ports if it has a value).
  4. Restart the SQL Server (SQLEXPRESS) service — in Configuration Manager under SQL Server Services, or via services.msc.
This is the common gotcha If you skip this, the MCP shows failed in claude mcp list even when your login and password are correct — the server just isn't reachable over TCP yet. Enabling TCP/IP on port 1433 is what lets Server=localhost,1433 in the connection string below resolve.

5.4  Register the MCP server with Claude Code

Claude Code manages MCP servers with the claude mcp command. There are several community SQL Server MCP servers; a Node-based one you can run via npx is the simplest to start with. The mssql-mcp-server package takes a single connection string rather than separate variables — note Server=localhost,1433 (a TCP address plus the port you set above). From your project folder:

Run in your terminal (exit Claude first, or use a second window)
claude mcp add sqlserver `
  --env "MSSQL_CONNECTION_STRING=Server=localhost,1433;Database=TaskTrackerDb;User Id=mcp_reader;Password=YourStrongPassword;TrustServerCertificate=true;Encrypt=false;" `
  -- npx -y mssql-mcp-server
Watch the connection string Keep it on one line, quoted, and end it with a semicolon. TrustServerCertificate=true and Encrypt=false are what let a local dev instance connect without a real TLS certificate. Swap in your own mcp_reader password.

The exact variable names and package differ between MCP servers — some take separate MSSQL_SERVER / MSSQL_USER settings and a named instance (localhost\SQLEXPRESS) instead of a connection string. Check the README of the one you pick (a few options are listed in Appendix D). The shape is always the same: a command Claude runs, plus connection settings.

Don't hand-edit config blindly claude mcp add writes the configuration for you. You can also inspect or hand-edit the generated MCP config file, but using the command avoids typos. Verify with claude mcp list — your server should appear and show Connected.

5.5  Use the MCP inside Claude Code

Start Claude Code again in the project. Confirm the server is live:

▶ Prompt to Claude Code

You should see sqlserver listed with its available tools. Now put it to work — Claude will call the MCP's tools (asking your approval) rather than guessing:

Then combine it with the codebase — this is where MCP shines:

Safety reminder Even read-only, treat the MCP like production access. Never point an MCP at a database with real customer data during a casual learning session, and never paste real credentials into a repo. Keep the mcp_reader password out of Git.
